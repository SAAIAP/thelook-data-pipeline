Architecture & Technology Choices

BigQuery

Data Warehouse

Serverless, petabyte-scale SQL warehouse. Source data already lives in bigquery-public-data — using the same platform eliminates transfer costs and latency.

Why not Snowflake/Redshift? Zero data movement; public dataset is native BQ.
dbt (BigQuery adapter)

ELT Transformation

SQL-native transforms with built-in testing, auto-generated lineage docs, and Git-versioned models. Staging views + mart tables keep costs low and query speed high.

Why not Spark? Data volume fits BQ SQL; no cluster overhead needed.
Python + pandas

Analysis & Visualisation

SQLAlchemy BigQuery connector provides a standard DB-API2 interface. pandas + seaborn + matplotlib produce reproducible, shareable charts in a Jupyter notebook.

Why not Looker Studio? Notebooks travel with the repo; no extra tool login.
dbt Tests

Data Quality

17 tests: uniqueness, not-null, accepted values, referential integrity, and 3 custom business-logic SQL tests. Pipeline fails loudly before bad data reaches analysts.

  • Positive sale price on completed orders
  • No orphan fact rows (FK integrity)
  • Gross margin outlier detection
GitHub Actions

Orchestration (CI/CD)

Zero-infra scheduler. Daily cron triggers ingest → dbt run → dbt test. Push-triggered run validates every PR before merge.

Why not Airflow? Airflow is heavy for a single pipeline; Actions is free & built-in.
Star Schema

Warehouse Design

Chosen over 3NF for faster OLAP queries. fact_sales at order-item grain allows roll-up to any dimension. Surrogate keys decouple marts from source ID changes.

Pre-computed: price_tier, age_bucket, margin_pct, running_revenue.

Star Schema Design

4 dimension tables + 1 central fact table at order-item grain.

┌─────────────────────┐ │ dim_date │ │ date_key (PK) │ │ year · quarter │ │ month · month_name │ │ is_weekend │ └──────────┬──────────┘ │ date_key FK ┌─────────────────────┐ ┌─────┴──────────────────────────────────────┐ ┌─────────────────────┐ │ dim_customer │ │ fact_sales │ │ dim_product │ │ customer_key (PK) ├───┤ order_item_id (PK) ├───┤ product_key (PK) │ │ user_id │ │ customer_key (FK → dim_customer) │ │ product_id │ │ first/last_name │ │ product_key (FK → dim_product) │ │ name · brand │ │ email │ │ date_key (FK → dim_date) │ │ category │ │ age · age_bucket │ │ sale_price │ │ department │ │ gender │ │ cost │ │ retail_price │ │ country · city │ │ gross_margin │ │ cost │ │ traffic_source │ │ gross_margin_pct │ │ margin_pct │ │ created_at │ │ discount_amount │ │ price_tier │ └─────────────────────┘ │ days_to_ship │ └─────────────────────┘ │ customer_running_revenue │ │ status · created_at │ └────────────────────────────────────────────┘
Grain

One row per order line item — finest granularity, supports any roll-up

Surrogate Keys

customer_key / product_key decouple marts from source ID changes

Pre-computed

price_tier, age_bucket, margin_pct — no repeated CASE in queries

Materialization

Staging = views (free); Marts = tables (fast queries)

Executive Presentation

10-minute deck for a mixed audience of technical (CTO, VP Eng) and business (CEO, CFO, COO) executives. Full slide content in reports/executive_presentation.md.

Slide 1–2 · 0–2 min
Executive Summary

Raw e-commerce data sitting in isolated tables cannot answer business questions. We built a fully automated ELT pipeline over 7 source tables (~125K+ orders), transforming them into a clean star schema with tested, version-controlled models.

Slide 3 · 2–4 min
Pipeline Architecture

BQ Public → Python ingest → dbt staging (views) → dbt marts (tables) → Jupyter. Each layer justified: BigQuery for no-infra scale, dbt for SQL-native ELT, GitHub Actions for zero-cost orchestration.

Slide 4–5 · 4–6 min
Schema Design & Data Quality

Star schema chosen for 3× fewer joins than 3NF. 17 dbt tests block bad data before it reaches analysts. Custom SQL tests enforce business logic (positive sale price, no orphan rows, margin outlier detection).

Slide 6–7 · 6–8 min
Key Business Findings
  • Consistent Q4 revenue peaks — seasonal inventory opportunity
  • Outerwear is the highest-revenue category
  • 35–44 age group drives largest revenue share
  • Top 10% of customers generate ~40% of revenue
  • Email-acquired customers have highest median CLV
Slide 8–9 · 8–10 min
Risks & Roadmap
  • Risk: Source schema change → mitigated by dbt tests
  • Risk: BQ cost overrun → mitigated by column selection in marts
  • 0–30 days: Connect Looker Studio to thelook_marts
  • 30–90 days: Incremental dbt models + cohort analysis
  • Strategic: Real-time streaming via Pub/Sub → BigQuery

How to Run

# 1. Install dependencies
pip install -r requirements.txt

# 2. Ingest raw data
python ingestion/ingest_thelook.py

# 3. Run dbt models
cd thelook_dbt && dbt deps && dbt run

# 4. Run data quality tests
dbt test

# 5. Open analysis notebook
cd .. && jupyter notebook notebooks/analysis.ipynb
Prerequisites
  • Google Cloud project with BigQuery enabled
  • Authenticated via gcloud auth application-default login
  • Python 3.10+ with packages from requirements.txt
  • dbt-bigquery installed
  • profiles.yml configured with your project ID
